# R5.1 Prior art: task trackers and agent orchestrators

Researched 2026-10-30 from docs, source and issue trackers (read-only; nothing installed). Star counts and activity are as of that date. Hands-on trials of the shortlisted tools are still open.

**Result:** no existing tool covers foreman's core. Build it ([D0002](../decisions/D0002-build-foreman.md)), and borrow the specific ideas listed below.

## Trackers built for agents

### Beads (`bd`) — github.com/gastownhall/beads
- MIT, Go, ~28k★, very active (v1.3.2, 2026-10-24), **~1,600 open issues**.
- **Storage has changed three times:** SQLite plus JSONL in git with a daemon, then hidden sync worktrees, now **Dolt**.
  - Dolt runs either embedded (single writer) or as a server (multiple writers).
  - Cross-machine sync goes through `refs/dolt/data` on the git remote. JSONL is now an export only.
- **Worktrees share the main checkout's `.beads` via the git common dir**, which is the same approach foreman plans to use. There are open bugs in exactly this area, including [#4767](https://github.com/gastownhall/beads/issues/4767): 8 parallel `claude -p` agents, and 7 of 8 `bd close` calls reported success but were not saved.
- **Strong parts:**
  - A ready queue built only from `blocks` edges (`bd ready`).
  - Atomic `ready --claim` and `close --claim-next`.
  - 5-minute leases with heartbeat and `reclaim`.
  - `discovered-from` links.
  - Merge slots (a mutex for each project).
  - **Gates:** `human`, `gh:run`, `gh:pr`, timer.
  - A SessionStart hook (`bd prime`) that re-injects a short workflow brief after compaction.
- **Weak parts:**
  - The agent being gated can resolve its own human gate ([#7370](https://github.com/gastownhall/beads/issues/7370)).
  - Issues have no acceptance-criteria field.
  - Too many features (molecules, swarm, federation).
  - MCP is a separate Python package. Beads itself recommends the CLI plus hooks over MCP.

### Backlog.md — github.com/MrLesk/Backlog.md
- MIT, TypeScript/Bun, ~7.2k★, active.
- **Storage:** one markdown file per task under `backlog/`, with YAML frontmatter and section markers (`<!-- AC:BEGIN -->`).
- **Strong parts:**
  - Each task has Acceptance Criteria, a project-wide **Definition of Done**, a Plan, Notes and a **Final Summary**.
  - `isReady` fails closed on unknown dependencies.
  - `backlog instructions` and MCP resources give guidance on demand instead of a huge AGENTS.md.
  - A web kanban that runs on localhost only.
  - An `onStatusChange` shell hook.
- **Its maintainer concedes it can't coordinate parallel worktrees** ([BACK-760](https://github.com/MrLesk/Backlog.md/blob/main/backlog/tasks/back-760%20-%20Share-task-IDs-assignment-and-status-across-branches-and-worktrees.md)): "a second agent can take the same task and neither is told."
  - The planned fix is a git ref with `update-ref` compare-and-swap, deliberately with no leases.
  - Facts worth keeping from that work:
    - Refs are visible across worktrees immediately.
    - With 20 parallel compare-and-swap writers, exactly one wins.
    - Shared values in task files conflict on merge even when adjacent lines change.
    - A take must succeed only on an *unassigned* task. In their test, counting "already the requested value" as success gave 40 winners for 8 tasks.

**claude-code-action** (MIT) and **codex-action** (Apache-2.0) trigger on mentions, labels, assignment or schedule, and support structured output. **Neither can approve, merge or rebase.**
- That makes them a good optional *remote verifier*: a clean runner, with pass/fail returned per check as structured output.
- They are a poor default worker for a local-first tool: slow cold start, cost, no shared state, and prompt-injection risk on public repos.

## What foreman does that none of these do

1. A shared SQLite claim and lease protocol that agents in parallel worktrees use through the CLI or MCP. Elsewhere, a UI or orchestrator owns the state.
2. Each task gets its own **database and port block**, recorded in shared state and reclaimed by the janitor. No worktree tool does per-task databases as a built-in feature.
3. A fresh-context verifier that checks the **acceptance checks attached to the task**, not a generic review.
4. Sign-off routed by risk class, which the agent being gated cannot resolve.

Delegatus covers part of 3 and 4, and YYLO covers risk-based merging. Both are tiny. Points 1, 2 and acceptance checks as structured data are new.
